# Conformance Testing

Language-agnostic test data for the A2UI turn record, specified in [`specification/turn_record/`](../specification/turn_record), for the capture paths that write it, and for the proxies replaying it. A fixture is a turn record.

## Suite Structure

Test suites are organized by area.

### Turn record (`turn_record/`)

- `turn_record/validator_v0_1.yaml`: validates each fixture against [`specification/turn_record/v0_1/json/turn_record.json`](../specification/turn_record/v0_1/json/turn_record.json). Every case uses `action: validate_turn_record`.
  - Must pass: one minimal fixture per event kind, `minimal_<kind>.json`, holding the turn event and one event of the kind with only the required fields (the `turn` kind's holds just the turn event); and two full records, each two turns of one of upstream's Python samples at 059b8d34, with every kind present and every optional part the sample produces:
    - `full_record_restaurant_finder.json`: a list whose first model request gets a `503` and is retried by the Gemini client, then a booking form whose model call is retried after a failed parse, with streamed responses. Its A2UI messages come from `samples/agent/adk/restaurant_finder/examples/0.9/`.
    - `full_record_custom_components.json`: a contact card with an org chart on the inline catalog, then the floor plan its `view_location` action reads over MCP with HTTP+SSE through the tool proxy. Its A2UI messages come from `samples/agent/adk/custom-components-example/examples/0.9/multi_surface.json` and from the floor plan `a2ui_examples.py` builds. Each JSON-RPC request is one `tool_call` event: its exchange is the POST, and its reply from the `GET /sse` stream is an `event: message` chunk on it. The stream's `endpoint` event is a chunk on `initialize`.
    - `full_record_retried_parse.json`: one turn of the A2UI step, assembled by hand from the wrapper capture suite's texts: the prompt generation of `direct_json_generate`, its UI section in both model calls' system prompts; a first Gemini call whose reply is the `surface_already_exists` text, parsed as a stream that fails on the second `createSurface` of the same surface; the call retried with the failure appended, its reply the `direct_json_parse_response` text, parsed whole; the delivery of that parse's messages; and the four checks passing. The viewer's tests of the inferred retry, the model call a parse read and the parse a component came from run on it, and its Flow 6 is walked on it, in Chromium by the tool's `src/viewer_end_to_end.test.ts`.
  - Also must pass: `prompt_generation_failed.json`, `parse_stream_read_past.json`, `parse_tool_call.json`, `chunk_with_id.json` and `check_with_skipped_surfaces.json`, hand-written minimal fixtures holding the optional attributes of closed attribute sets that neither full record holds: a toolset's failed prompt generation, with its `error.type`, its `exception` event, the SDK and the tool; a stream that read past two rejected blocks, with its chunk events and an `exception` event per block, with the block's range and the SDK's details; a toolset's parse, unwrapped, with the tool, the call's id and the object the tool returned; a chunk's `event` and `id`; and a check's skipped surfaces with a catalog id and both reasons.
  - Must fail: a minimal fixture broken in one place, named for what it breaks. At least one case breaks each unit of the schema: the top level, each shared definition, each kind's rules, the turn's one turn event, and the rule on GenAI content.

### A2A capture (`a2a_capture/`)

- `a2a_capture/capture_v0_1.yaml`: replays A2A traffic recorded once from every entry of the coverage roster through the A2A capture path, and compares the turns it captures with the expected record. Every case uses `action: capture_a2a`. The data is under `test_data/a2a_capture/v0_1/<entry>/`: each conversation's recording as `<conversation>.har`, HAR 1.2, and its expected record as `<conversation>.json`, a turn record v0.1 file holding the conversation's turns.
- A harness starts a replay server that answers each recorded request with its recorded response, puts the capture path in front of it, and sends each recorded request in order. It checks that the host received each response as recorded, a card with only its JSON-RPC endpoints pointed at the capture path, and that the turns captured match the expected record. The comparison takes exact values for everything the traffic determines. The trace ids, span ids, times and the writer's version are Spectra's own: the expected record carries schema-valid stand-ins for them, which the comparison skips, and the harness checks instead that each turn's events share one well-formed trace id, that each wire event's parent is the turn event, and that the turn's start, its wire events and its end are in time order. Spectra's harness is `tools/spectra/src/a2a/capture.conformance.test.ts`.

#### Recording

A recording is made at the entry's pinned commit or version, and stays as made while it holds something Spectra supports. At each move of the upstream pin the roster is reviewed: a recording that holds only what Spectra no longer supports is recorded again when its entry still runs and now sends a supported form, and is retired otherwise; an axis left without an entry goes to an agent built for it.

- [`_dev/tools/record_a2a_traffic.py`](../_dev/tools/record_a2a_traffic.py) is the recording proxy: it relays each exchange between the host and the agent, rewrites the card it serves so the host's calls come back through it, and writes each exchange as the agent answered it. A recording keeps only `content-type`, `accept`, `A2A-Version`, `X-A2A-Extensions` and `A2A-Extensions`, so no credential is written. A response whose connection broke before it ended keeps the bytes that arrived and carries HAR's custom field `_brokenOff`.
- [`_dev/tools/send_a2a_requests.py`](../_dev/tools/send_a2a_requests.py) sends a conversation's requests, from its request file under [`_dev/tools/a2a_requests/`](../_dev/tools/a2a_requests/), for the entries no host reaches.
- [`_dev/tools/write_a2a_capture_records.py`](../_dev/tools/write_a2a_capture_records.py) writes each expected record from its recording, by the rules of `_dev/docs/spec/task-2.2-a2a-adapter.md`, sharing no code with the capture path.

All fixtures are located in `test_data/`, under `test_data/<area>/<version>/`, and are exempt from Prettier. [`test_data/catalogs/`](test_data/catalogs/) holds catalog definitions the tool's tests configure, named in its README; they are not cases of a suite. The turn record v0.1 fixtures and their case list were written by [`_dev/tools/make_fixtures.py`](../_dev/tools/make_fixtures.py), which reads upstream's samples at 059b8d34 and computes the full records' component ranges, timings and repeated content, up to Phase 5's documents; they have been edited by hand since, and the script no longer reproduces them.

### Model capture (`model_capture/`)

- `model_capture/capture_v0_1.yaml`: replays model API traffic through the model proxy, with [the stand-in provider](#the-stand-in-provider) in the provider's place, and compares the `model_call` events it writes with the expected record. Every case uses `action: capture_model`. The data is under `test_data/model_capture/v0_1/<entry>/`: each recording as `<conversation>.har`, HAR 1.2, and its expected record as `<conversation>.json`, a turn record v0.1 file holding one turn with a stand-in turn event and one model call per exchange.
- A harness starts the stand-in with the recording, opens one turn, sends each recorded request through the model proxy under the prefix of the provider's variable, checks that the agent's side received each response as recorded, closes the turn, and compares the calls the turn holds with the expected record. The comparison takes exact values for everything the traffic determines. The trace ids, span ids, times, the time to the first chunk, where the request went and the headers the replay adds are Spectra's own: the expected record carries schema-valid stand-ins or leaves them out, the comparison skips them, and the harness checks instead that each call is under the turn event, ends after it starts and went to the stand-in. A case with `readInFull: false` leaves the stand-in unnamed, so every call is recorded raw, as a call to a host that is not a provider's is. Spectra's harness is `tools/spectra/src/model_proxy/capture.conformance.test.ts`.

### Tool capture (`tool_capture/`)

- `tool_capture/capture_v0_1.yaml`: runs client scenarios through the tool proxy to [Spectra's own tool server](#the-tool-server), and compares the `tool_call` events the proxy writes with the expected record. Every case uses `action: capture_tool`. The expected records are under `test_data/tool_capture/v0_1/<scenario>/<transport>.json`, each a turn record v0.1 file holding one turn with a stand-in turn event and the scenario's tool calls. No HAR is recorded for tools.
- A harness starts the tool server, and for each case runs its named scenario over each transport the case names, with the TypeScript MCP SDK's own client, or with plain HTTP requests for the routes, through the tool proxy with one turn open. It closes the turn and compares the tool calls it holds with the transport's expected record, after times, span ids, session ids, JSON-RPC request ids and the server's port are normalised and the headers the HTTP client and server add on their own are left out; it checks instead that each call is under the turn event, ends after it starts and went to the tool server. Spectra's harness is `tools/spectra/src/tool_proxy/capture.conformance.test.ts`.

| Transport              | The tool server's endpoint                             |
| ---------------------- | ------------------------------------------------------ |
| `streamable_http`      | `/mcp`, MCP over streamable HTTP, each reply a stream  |
| `streamable_http_json` | `/mcp/json`, MCP over streamable HTTP, each reply JSON |
| `http_sse`             | `/sse` and `/messages`, MCP over HTTP+SSE              |
| `http`                 | The plain HTTP routes                                  |

The expected records were written by the harness from its first capture, with `SPECTRA_WRITE_TOOL_CAPTURE=1`, and checked by hand against the rules of `_dev/docs/spec/task-5.3-tool-proxy.md`.

### Model replay (`model_replay/`)

- `model_replay/replay_v0_1.yaml`: runs each model capture case against its expected record instead of the provider. Every case uses `action: replay_model` and names the same recording and expected record as the capture case of its name; there are no recordings of its own.
- A harness arms the model proxy with the expected record in everything-recorded mode, its targets at an origin where nothing listens and its calls' `url.full` moved there, opens one turn and sends each recorded request through the proxy under the prefix of the provider's variable. It checks that the agent's side received each reply as recorded, compared by server-sent events, each one's data by JSON value, or by the body's JSON value, a broken-off reply breaking. It closes the turn and compares the calls the turn holds with the expected record by the capture suite's comparison, each call's `a2ui.replay.served_from` the span id of the recorded call at its place. Then, against the record again, it sends the first request read in full, else the first request, with the last string value of its body changed: the agent's side gets the `502` with the proxy's one line, the terminal gets that line, and the turn holds a failed call with `error.type` `replay_miss` and no response attributes. Spectra's harness is `tools/spectra/src/model_proxy/replay.conformance.test.ts`.

### Tool replay (`tool_replay/`)

- `tool_replay/replay_v0_1.yaml`: runs each tool capture scenario against its expected records instead of the tool server. Every case uses `action: replay_tool` and names the same scenario and expected records as the capture case of its name.
- A harness makes each expected record concrete, `<origin>` an origin where nothing listens, `<session-N>` a session id, and `<id-N>` the id the SDK's client numbered it, N - 1, then arms the tool proxy with it and runs the scenario over the transport with one turn open. The plain HTTP routes' replies are checked against the recorded calls, by server-sent events or by JSON value. It closes the turn and compares the calls it holds with the expected record by the capture suite's comparison, with the events the server initiated, `kind` `4`, dropped from the expected side, as replay does not re-send them, and the answers the protocol fixes, a notification's and a client's response's `202`, compared without their response headers. Every other call names the recorded call it was served from in `a2ui.replay.served_from`, and those answers name none. Then, against the record again, a client calls the first recorded `tools/call` with one argument changed, or `echo` when the scenario calls no tool, or the routes take a `POST` with a changed body: the call fails with the `502`, under HTTP+SSE the call posted on a carrier the harness opens itself, which then carries the request's JSON-RPC error, code `-32603` with the proxy's line as its message, the terminal gets the proxy's one line, and the turn holds a failed call with `error.type` `replay_miss` and no response attributes. Spectra's harness is `tools/spectra/src/tool_proxy/replay.conformance.test.ts`.

### Receiver capture (`receiver_capture/`)

- `receiver_capture/capture_v0_1.yaml`: posts the OTLP/JSON export requests recorded from a live run to the OTLP/HTTP receiver, and compares the turns it writes with the expected record. Every case uses `action: capture_receiver`. The data is under `test_data/receiver_capture/v0_1/<case>/`: `exports.json`, the run's export requests to `/v1/traces` and `/v1/logs` in arrival order, each with its path, its arrival time and its OTLP/JSON body; and `expected.json`, a turn record v0.1 file holding the turns the case opens, each with its turn event, its proxies' calls and the events the receiver wrote, its wire and check events left out.
- A harness starts the receiver's listener and posts each export in order. It opens each turn of the expected record before the first export that arrived at or after the turn's start, placing its proxies' calls in it without their links, and closes each turn before the first export that arrived after the turn's end, so that what arrived before a turn opened or after it closed reaches the receiver as it did live. Once every export is read and every turn written, it compares each turn as the store holds it with the expected record's, exactly, and the receiver's lines with the case's `log`. Spectra's harness is `tools/spectra/src/receiver/capture.conformance.test.ts`.

### Wrapper capture (`wrapper_capture/`)

- `wrapper_capture/capture_v0_1.yaml`: runs each case's job through a driver per language, which calls upstream's agent SDK at the pin with the A2UI wrapper switched on, and compares the turn the receiver writes with the expected record. Every case uses `action: capture_wrapper`. The data is under `test_data/wrapper_capture/v0_1/<case>/`: `input.json`, the driver's job, as [Writing cases for `capture_wrapper`](#writing-cases-for-capture_wrapper) has it; `text.txt`, the case text; `chunks.json`, a stream's chunk boundaries; and the expected record, `expected.json` when the languages share it, else `expected_python.json` and `expected_typescript.json`.
- **The drivers.** `wrapper_driver/python/`, a uv project run as `uv run --project wrapper_driver/python python wrapper_driver/python/driver.py <job>`, and `wrapper_driver/typescript/`, a package run as `node wrapper_driver/typescript/dist/driver.js <job>` after its own build, from `conformance/`. Each one's own project file brings in its wrapper, `a2ui-spectra-instrumentation`, and the agent SDK at the pin. The Python driver is a member of the repository's root uv workspace, beside the wrapper, and depends on `a2ui-agent-sdk`, `a2ui-core` and `a2ui-a2a` at the pin, through the uv git sources in the root `pyproject.toml`, and on `a2ui-adk` 0.3.0 from PyPI; `uv sync --all-packages` at the root syncs it, on the Python the root's `.python-version` names, 3.12. The TypeScript driver is a private workspace package built by its own `build` script, which the tool's `test` target depends on, and depends on the wrapper as a workspace package and on `@a2ui/agent` 0.1.0, built at the pin, through the root `package.json`'s `resolutions`; it loads the basic catalogs from its own copies of the pin's two files, `catalogs/basic_v0_9.json`, serving v0.9 and v0.9.1, and `catalogs/basic_v1_0.json`, through the SDK's `FileSystemCatalogProvider` with the job's catalog id. A driver takes the job's path as its one argument and reads the variables `run` sets, `OTEL_EXPORTER_OTLP_ENDPOINT` and `OTEL_EXPORTER_OTLP_PROTOCOL`. It switches the wrapper on with its one-line form, which starts the tracer provider from those variables, and runs the job on the processor the job describes:
  - `generate`: the processor's prompt, which its format's prompt generator writes;
  - `parse_response`: the whole text, with `wrapped`;
  - `open_stream`: a stream with `wrapped` and `afterRejectedBlock`, fed each chunk in order, stopping at the first that raises, and closed unless one raised;
  - `compile`: the text as one block, through the processor's parser;
  - `tool_call`: `a2ui-adk`'s `SendA2uiToClientToolset` tool on the processor, a renderer state bound to it when `rendererState` is true, run with the text as its `a2ui_payload` argument and a context that names no call id. The TypeScript driver fails a `tool_call` job as unknown.

  The driver lets the SDK's expected error pass and exits 0, the provider's shutdown flushing the export. A failure of its own exits non-zero with its message on stderr, and fails the case. No trace context is handed to it.

- **The harness** starts the receiver's listener and opens one turn, from the expected record's turn event with fresh ids and the present as its start, placed by its time window and open while the driver runs. A job with `beforeTurn` runs its driver first and opens the turn after, with the expected record's proxy calls placed in it. The harness then closes the turn and compares the turn as written with the expected record of the driver's language. Spectra's harness is `tools/spectra/src/receiver/wrapper_capture.conformance.test.ts`.
- **The comparison** skips, and checks well-formed instead, as the A2A capture suite does: trace, span and parent ids, a parent present where the record has one; every time, each event's span events in time order within it; the writer's version; `otel.scope.version`; `exception.stacktrace`, present where the record has one; and `a2ui.sdk.name` and `a2ui.sdk.version`, which must name the language's package, `a2ui-agent-sdk` or `@a2ui/agent`, and a version. A received attribute holding the JSON text of an array or an object is compared by the value it parses to. Everything else is compared exactly, messages and class names included, and the receiver prints no line.
- **The cases**, thirty-eight, each naming the languages it runs in: Direct JSON and Express in both, Elemental, Atom and the toolset in Python. `generate_failed`, Direct JSON on catalogs of mixed protocol versions, runs in TypeScript only: Python's agent SDK rejects the catalogs when the format is built, before the generator. `direct_json_open_stream_rejected_while_arriving` is a Direct JSON stream that rejects a block by its own check while a message arrives, a component id repeated, and reads past it, the chunk that brings the rejection finishing the block before it.

The expected records were written by the record-writer and checked by hand; `SPECTRA_WRITE_WRAPPER_CAPTURE=1` makes the harness write each from what it captures instead, for the drivers' sub-tasks.

#### The recordings

- [`_dev/tools/record_wrapper_replies.py`](../_dev/tools/record_wrapper_replies.py) is the recorder. For each inference format it builds the agent SDK's processor on the basic catalog at v1.0, generates the format's prompt with the SDK, sends it with one fixed user message, a card for one restaurant with its name, address, a rating and a button, to Gemini as a stream, and keeps the reply as the chunks arrived. The reply is parsed with the SDK before it is saved, and the model asked again when it does not parse. It writes each valid case's text: the joined reply for `<format>_parse_response`, with the chunk boundaries for `<format>_open_stream`, and the reply's first block for `<format>_compile`, `express_parse_response_unwrapped` and the toolset's two valid cases. Each saved reply was checked by hand once. The error cases' texts are written by hand.
- [`_dev/tools/write_wrapper_capture_records.py`](../_dev/tools/write_wrapper_capture_records.py) is the record-writer. For each case and language it reads the facts the record states off the pinned SDK, with [`wrapper_capture_facts.py`](../_dev/tools/wrapper_capture_facts.py) and [`wrapper_capture_facts.mjs`](../_dev/tools/wrapper_capture_facts.mjs): the section the generator wrote, or the messages the parse produced, those before an error included; each error's class, message and structured details, a details array whose every item is an object; and the object the toolset returned. It writes the events in the turn record's shapes, with stand-ins for ids and times. An error belongs to the block that was being compiled, or whose messages were being applied, when it was raised, its range where that block's text, as the SDK's parser unwraps it, sits in the input; for a stream, the block is found by feeding the text again one character at a time, as the last block opened when the error comes; an error raised after every block, by the tree check or by the toolset's validation of the whole payload, belongs to no block, and so does one the toolset's tool raises itself. For the toolset, it takes every error the tool swallows, read as the tool logs it. It writes one record when the languages come out equal, and one per language otherwise.

The Python records' prompt sections are the agent SDK's on Python 3.12: on 3.14 it writes Column's `justify` values in another order.

The prompt records, the six Python ones and the four TypeScript ones of `direct_json_generate`, `express_generate`, `elemental_generate`, `atom_generate`, `express_generate_two_catalogs` and `generate_outside_turn`, were read off the pin, upstream main `0888f88b2`: `a2ui-agent-sdk` 0.11.1.dev45 in the repository's environment on Python 3.12, and `@a2ui/agent` 0.1.0 built in the `a2ui-upstream` worktree, on Node 22. ## The stand-in provider

[`stand_in_provider/stand_in_provider.ts`](stand_in_provider/stand_in_provider.ts) is a server that replays recorded model API traffic at one origin, for the four APIs the model proxy reads in full and for any other call. Run it from `conformance/` after `yarn build`, as `node dist/stand_in_provider/stand_in_provider.js --port 9830 --har <file>`.

| Option         | Meaning                                                                                  |
| -------------- | ---------------------------------------------------------------------------------------- |
| `--port <n>`   | The port to listen on, on 127.0.0.1. Default: `$PORT`, or 9830.                          |
| `--har <file>` | A HAR 1.2 file to play. Can be repeated; the files play in order, the exchanges in each. |

It answers each request with the next recorded response, sends a stream in pieces, and answers a request it did not expect with a `599` naming what it expected. A request is expected when its method and path match the next recorded request's, the parameters that carry credentials left out of both. A response recorded with HAR's `_brokenOff` breaks off after its bytes.

Spectra reads the stand-in as the provider's own host when the test-only environment variable `SPECTRA_PROVIDER_STAND_IN` names its origin: a call forwarded there is read as the own host of the API its path names. The variable is for the tests and the acceptance run; it is not in the tool's usage or help. The model capture suite sets it for each case, and the acceptance run drives the custom-components example against the stand-in playing `openai_chat/custom_components_conversation.har` or `openai_responses/custom_components_conversation.har`, with `OPENAI_BASE_URL` pointed at the stand-in in Spectra's environment and the variable set to its origin.

## The tool server

[`tool_server/tool_server.ts`](tool_server/tool_server.ts) is Spectra's own tool server, on the TypeScript MCP SDK's low-level server, serving MCP over streamable HTTP and over HTTP+SSE and a few plain HTTP routes on one port. Run it from `conformance/` after `yarn build`, as `node dist/tool_server/tool_server.js --port 9831`; `--port` defaults to `$PORT`, or 9831.

| Route                                       | What it serves                                                                     |
| ------------------------------------------- | ---------------------------------------------------------------------------------- |
| `POST`, `GET` and `DELETE` `/mcp`           | MCP over streamable HTTP, stateful, each reply a stream of server-sent events      |
| `POST`, `GET` and `DELETE` `/mcp/json`      | The same, each reply JSON                                                          |
| `GET /sse`, `POST /messages?sessionId=<id>` | MCP over HTTP+SSE, the endpoint relative                                           |
| `GET` and `POST` `/api/json`                | A JSON route echoing the method, the query and the body                            |
| `GET /api/events`                           | A server-sent-event route: two `tick` events with ids, then one with no event name |
| Anything else                               | `404`                                                                              |

Its MCP side is the same over every transport: the tools `echo`, answering with its arguments; `fail`, answering with `isError`; `progress`, sending `notifications/progress` when the request asks for progress and `notifications/message` while it runs; and `ask`, asking the client through `sampling/createMessage` and answering with the client's text; a JSON-RPC error, `-32602`, for any other tool; the resource `spectra://tool-server/readme`; and the prompt `greet`, taking `name`.

## Writing cases for `validate_turn_record`

| Field         | Required      | Meaning                                                            |
| ------------- | ------------- | ------------------------------------------------------------------ |
| `name`        | yes           | Unique name of the case.                                           |
| `description` | for must-fail | What the case verifies. For a must-fail case, the reason it fails. |
| `action`      | yes           | `validate_turn_record`.                                            |
| `fixture`     | yes           | Path of the fixture, relative to `conformance/`.                   |
| `expectError` | for must-fail | The failure the fixture must produce.                              |

A case without `expectError` passes when the fixture validates. A case with it passes when the fixture fails validation and every entry of `expectError.details` matches at least one reported error:

```yaml
- name: turn_without_outcome
  description: The turn event has no outcome.
  action: validate_turn_record
  fixture: test_data/turn_record/v0_1/turn_without_outcome.json
  expectError:
    category: ValidationError
    details:
      - path: /turns/0/events/0/attributes
        code: required
```

`path` is the JSON Pointer to the failing value in the fixture, and `code` is the keyword that failed, as JSON Schema 2020-12's output format names them. Ajv reports a failed `contains`, `minContains` and `maxContains` alike as `contains`, so the harness counts the matching items to name the one that failed.

The harness validates with Ajv 8's draft 2020-12 build in strict mode, with Ajv's `strictTypes` and `strictRequired` checks off. It loads the copied GenAI schemas under their addresses relative to `turn_record.json`'s `$id`, and the draft-07 meta-schema that `gen-ai-tool-definitions.json` references. `format` is an annotation and is not checked.

| `expect`      | yes      | The expected record of each transport the scenario runs over, `streamable_http`, `streamable_http_json`, `http_sse` or `http`, relative to `conformance/`. |

```yaml
- name: session_end
  description: "MCP's session end under streamable HTTP: a DELETE carrying Mcp-Session-Id, named DELETE, with the session and no method."
  action: capture_tool
  scenario: session_end
  expect:
    streamable_http: 'test_data/tool_capture/v0_1/session_end/streamable_http.json'
```

A new scenario is written in the harness, which runs it with the MCP SDK's client against the tool server; its expected records are written with `SPECTRA_WRITE_TOOL_CAPTURE=1` and checked by hand.

## Writing cases for `capture_wrapper`

| Field              | Required | Meaning                                                                                                                                                                               |
| ------------------ | -------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `name`             | yes      | Unique name of the case.                                                                                                                                                              |
| `description`      | yes      | What the job does and what the case verifies.                                                                                                                                         |
| `action`           | yes      | `capture_wrapper`.                                                                                                                                                                    |
| `job`              | yes      | Path of the driver's job, relative to `conformance/`.                                                                                                                                 |
| `expect`           | yes      | Path of the expected record, relative to `conformance/`, when the languages share it; else a map from each language, `python` and `typescript`, to its own.                           |
| `expected_to_fail` | no       | A map from a language to why the case fails there at the pin, starting with the owning sub-task as `Sub-task N.M, at the pin: `. The case still runs, as Node's test runner's `todo`. |

```yaml
- name: express_open_stream
  description: 'The Express reply read as a stream, its chunks as Gemini sent them.'
  action: capture_wrapper
  job: 'test_data/wrapper_capture/v0_1/express_open_stream/input.json'
  expect: 'test_data/wrapper_capture/v0_1/express_open_stream/expected.json'
```

The job is a JSON object, `WrapperCaptureJob` in `conformance_schema.json`:

| Field                | Required                     | Meaning                                                                                                                                                                                                                                          |
| -------------------- | ---------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `languages`          | yes                          | The languages the case runs in: `python`, `typescript`.                                                                                                                                                                                          |
| `inferenceFormat`    | yes                          | The processor's inference format: `direct_json`, `express`, `elemental` or `atom`.                                                                                                                                                               |
| `entryPoint`         | yes                          | What the driver calls: `generate`, `parse_response`, `open_stream`, `compile` or `tool_call`.                                                                                                                                                    |
| `catalogs`           | yes                          | The processor's catalogs, in order, each by `catalogId` and `protocolVersion`, in the record's form. One with a `path`, relative to `conformance/`, is that `catalog.json`; one without is the basic catalog of its version, built into the SDK. |
| `examples`           | no                           | Path of the prompt's example turns, a JSON list of lists of A2UI messages, relative to the job's directory.                                                                                                                                      |
| `text`               | except for `generate`        | Path of the case text, relative to the job's directory: the whole text, the one block, the stream's text, or the `a2ui_payload`.                                                                                                                 |
| `chunks`             | for `open_stream`, only then | Path of a JSON list of each chunk's end in the text, in UTF-16 code units.                                                                                                                                                                       |
| `wrapped`            | no                           | `false` when the whole text is one block without tags. `true` by default.                                                                                                                                                                        |
| `afterRejectedBlock` | no                           | What a stream does after it rejects a block: `end`, the default, or `continue`.                                                                                                                                                                  |
| `rendererState`      | no                           | For `tool_call`: whether a renderer state is bound to the processor. `false` by default.                                                                                                                                                         |
| `beforeTurn`         | no                           | Whether the driver runs before the turn opens. `false` by default.                                                                                                                                                                               |

A new case's valid text is recorded with the recorder, its error text written by hand, and its expected records written with the record-writer and checked by hand.

## Checks on the test data as a whole

- Every kind the schema defines appears in at least one must-pass fixture.
- Every file under `test_data/turn_record/` is named by a case.
- Every expected record of the A2A, model, tool, receiver and wrapper capture suites validates against the turn record schema.
- Every job of the wrapper capture suite matches `WrapperCaptureJob` in `conformance_schema.json`, and a case with a record per language names one for each language its job runs in.
- Every file under `test_data/a2a_capture/`, `test_data/model_capture/`, `test_data/tool_capture/`, `test_data/receiver_capture/` and `test_data/wrapper_capture/` is named by a case: for the wrapper capture suite, by its job, the files the job names, or its expected records.
- Every case of the model and tool replay suites names a capture case of its name, and that case's recording or scenario and expected records.

## Commands

From `conformance/`:

- `yarn build`: compiles the harness in `tests/`, the stub agent in `stub_agent/`, the stand-in provider in `stand_in_provider/` and the tool server in `tool_server/` into `dist/`.
- `yarn test`: builds, then runs the suites with Node's test runner.
- `yarn lint` and `yarn lint:fix`: ESLint with the root ESLint preset.
- `yarn format` and `yarn format:check`: Prettier, with the root `.prettierignore`.

From the repository root, `yarn build:all`, `yarn test:all`, `yarn lint:all` and `yarn format:check:all` run the same across every workspace.
